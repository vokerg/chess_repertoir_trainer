# ACT-002 — Authoritative in-app activity producers

Issue: [#247](https://github.com/vokerg/chess_repertoir_trainer/issues/247)

Status: COMPLETE

## Producer integration

The existing server-owned completion transitions now record activity through `ActivityFeedService`:

- web repertoire sessions record `REPERTOIRE_LINES_TRAINED` on the first `IN_PROGRESS` to `PASSED` or `FAILED` transition;
- completed mobile offline attempts record the same activity in the attempt persistence transaction using the client `completedAt` timestamp;
- Lichess puzzle rounds record `LICHESS_PUZZLES_COMPLETED` only when the optimistic round update first changes `IN_PROGRESS` to `COMPLETED`;
- tactical scenarios record `TACTICAL_SCENARIOS_COMPLETED` only on the first completion of a session containing at least one attempt;
- client and worker game-analysis runs record `GAME_ANALYSES_COMPLETED` in their repository transaction when a run first becomes completed.

## Idempotency and transaction boundaries

Web completion and abandonment use guarded terminal transitions, so concurrent or repeated requests cannot overwrite one terminal result with another. Mobile retries remain protected by the existing `(userId, clientAttemptId)` unique key. Mobile persistence acquires the activity/user lock before inserting child rows, keeping the transaction lock order consistent with the activity service. Puzzle optimistic concurrency prevents a stale completion from being saved twice. Scenario completion is conditional on `IN_PROGRESS`. Worker analysis completion is conditional on `RUNNING`, while concurrent equivalent client-summary submissions serialize on the imported game and reuse one completed run.

Each activity increment is committed in the same transaction as its authoritative completion. Activity dates derive from the source completion timestamp and the persisted user IANA time zone. No browser or mobile client emits a separate activity event.

## Deliberate exclusions

Played-game day reconciliation remains ACT-003. No Angular UI or imported-game count reconciliation is included here.

## Validation

Coverage verifies web and mobile repertoire parity, concurrent or repeated web/mobile completion handling, puzzle completion versus repeated updates, attempted versus empty tactical scenarios, worker retry safety, and concurrent client-summary reuse.
