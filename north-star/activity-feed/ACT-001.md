# ACT-001 — Activity ledger and daily-goal API

Issue: [#246](https://github.com/vokerg/chess_repertoir_trainer/issues/246)

Status: COMPLETE

## Delivered contract

The activity foundation is one authenticated Fastify module:

- `GET /api/me/activity?from=YYYY-MM-DD&to=YYYY-MM-DD`
- `GET /api/me/activity/today`
- `GET /api/me/activity/preferences`
- `PUT /api/me/activity/preferences`

All responses derive ownership from the authenticated `userId`. History ranges are inclusive, limited to 366 calendar days, return ISO date-only values, and are ordered newest day first with activities in the versioned vocabulary order.

The Today response returns all five activity types, including zero-count entries, and computes the static product goals server-side.

## Persistence

`UserActivityDailyAggregate` stores one row per `(userId, activityDate, type)` with count, first/last occurrence timestamps, and normal audit timestamps. A database unique key and validation checks prevent duplicate or invalid aggregates.

`AppUser.timeZone` stores the effective IANA zone and defaults to `UTC`.

The repository exposes two write modes through `ActivityFeedService`:

- `recordIncrement(...)` for first authoritative completion transitions;
- `reconcileDaily(...)` for absolute source-derived facts such as imported games.

Increment is one atomic PostgreSQL upsert: concurrent writers add to the same unique row while preserving the earliest and latest occurrence timestamps. Reconciliation uses the same key but replaces the aggregate with the authoritative absolute count and occurrence bounds.

Both service methods accept an optional Prisma transaction. ACT-002 producers can therefore record activity in the same transaction as the authoritative completion transition; standalone callers receive a short activity-owned transaction. The transaction locks the owning `AppUser` row while deriving the persisted time zone, which serializes activity writes with preference changes and prevents a first write from racing a calendar-boundary change.

## Time-zone safety

Invalid IANA zones are rejected. A zone can be set before activity exists and can be submitted repeatedly without change. Changing to a different zone after aggregates exist returns `TIME_ZONE_CHANGE_REQUIRES_REBUILD`; this prevents mixed calendar-day history until the explicit historical reconciliation path is added by ACT-003.

Absolute reconciliation verifies that non-null first/last occurrences belong to the supplied activity day in the current effective zone. A caller that grouped source facts under a stale zone must regroup and retry rather than silently writing a mismatched bucket.

## Deliberate exclusions

This issue does not instrument training, puzzles, scenarios, analyses, or imports and does not add Angular UI. Those remain ACT-002, ACT-003, and ACT-004.

## Validation

Coverage includes:

- shared-contract parsing and rejection of arbitrary activity names;
- IANA validation and a Copenhagen midnight boundary;
- deterministic history and Today goal mapping;
- concurrent atomic increment and absolute reconciliation behavior;
- caller-owned transaction participation;
- authenticated HTTP ownership and preference errors;
- generated OpenAPI operation IDs and response declarations.
